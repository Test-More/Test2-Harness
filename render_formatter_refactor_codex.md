# Render / Formatter Refactor Notes For Planning

This document is a companion to `render_formatter_refactor`. It is intended
for an agent writing an implementation plan. It does not supersede the root
proposal; it calls out design constraints, risks, and a likely staging shape.

## High-Level Take

The proposed direction is sound: renderers should pull from durable log
artifacts instead of receiving a push stream of every event. That model fits
yath 2.0 better for replay, quiet-verbose-on-failure behavior, cached display
formats, and future server/UI rendering.

The biggest implementation risk is not formatter extraction. The biggest risk
is replacing the current `Driver` behavior safely. Today the driver does more
than tail events: it derives run/job lifecycle state from log records and
artifact lookups, then emits synthetic lifecycle facets expected by existing
renderers. The new design needs an explicit replacement for that lifecycle
derivation.

## Recommended Names

Use these three top-level categories:

* **Renderer** - Reads producer/artifact state and emits live or replayed output
  to a sink.
* **Formatter** - Converts one artifact plus context into a target format.
* **Finalizer** - Runs at end-of-run to produce final output or perform final
  side effects.

`Finalizer` is a good fit for current `Summary`, `Notify`, and `ResetTerm`.
These do not need to render every producer continuously.

Avoid names like `Trigger` unless the category is only for side effects. Summary
output is not really a trigger.

## Formatter Boundary

Prefer leaf-only formatters:

* Input: one artifact, formatter settings, and a context struct.
* Output: bytes or a stream of bytes in the requested format.
* No recursive calls back into the log handle to fetch other artifacts.

Renderers should compose multiple formatted artifacts when needed. This keeps
formatter caching, dependency tracking, parallelization, and testing much
simpler.

If a formatter is allowed to fetch other artifacts, every cache key must encode
the full transitive dependency graph. That will make invalidation difficult and
will blur the renderer/formatter distinction.

## Cache Key Requirements

Do not key cached formatter output only by artifact, formatter name, and
formatter version. Include all settings that can affect the generated bytes.

Likely cache key fields:

* Source artifact identity and sealed generation/revision.
* Source artifact content hash or equivalent immutable identifier.
* Formatter name.
* Formatter implementation version.
* Output-affecting formatter settings.
* Relevant renderer/display settings when the formatter output embeds them.

For `tty` and `text`, consider whether these can affect bytes:

* Verbosity/detail level.
* Color/theme choice.
* ANSI enabled/disabled.
* Terminal width, if wrapping or truncation is performed.
* Stable ordering mode, if any ordering policy is configurable.

If terminal width affects output, either include it in the key or keep wrapping
out of the cached formatter output.

## Cache Storage And Concurrency

The plan should define cache-write semantics before implementation.

Directory/extracted logs:

* Write to a temp file in the same directory.
* Flush/close.
* Atomically rename into place.
* Treat existing cache as winner if another process completed first.

DB logs:

* Use a uniqueness constraint or equivalent compare-and-insert behavior for the
  cache key.
* Treat duplicate insert as success and read the existing blob.

Tarball logs:

* Read-only. Do not attempt cache writes.

Version metadata:

* Prefer version metadata embedded inline in each cached blob.
* A root meta artifact can act as an index/summary, but should not be the only
  authority needed to validate a blob.

Compression:

* zstd-compressed sealed blobs are reasonable.
* For append-capable formats, concatenated zstd frames are reasonable only if
  the reader path explicitly supports them.

## Producer Notification Layer

The plan should define a reusable watcher/lifecycle layer, not duplicate log
loop logic in every renderer.

Recommended shape:

* A log watcher reads live or sealed logs.
* It derives producer lifecycle notifications from log contents.
* It exposes the same notification stream to renderers regardless of log
  backend.
* Renderers declare interests/subscriptions up front.
* The watcher only tails partial artifacts requested by at least one renderer.

Notification kinds likely needed:

* `producer_started`
* `producer_progress`
* `producer_sealed`
* `artifact_available`
* `artifact_progress` for explicitly tailed artifacts
* `artifact_sealed`

Producer descriptors should be stable data, not event objects. They should
include enough identity and parentage to let renderers fetch related artifacts:

* Producer type: run, job, service, collector, etc.
* Run id.
* Job id / try number where applicable.
* Parent producer id where applicable.
* Start/end/sealed timestamps if known.
* Artifact references by kind.
* Status summary when known.

## Important Migration Risk

The current `Driver` is a compatibility bridge. It reads events, derives
lifecycle state, lazy-loads job spec/report artifacts, and emits synthetic
facets. A plan that simply deletes `Driver` and moves the loop into renderers
will likely duplicate this logic and make behavior diverge across renderers.

Better staging:

1. Extract producer/lifecycle derivation from `Driver` into a reusable watcher
   or producer-index component.
2. Keep the old `OutputManager` path temporarily by adapting watcher
   notifications back into the existing synthetic event stream.
3. Add formatter infrastructure and cache API.
4. Convert the default terminal output to the new pull model first.
5. Convert finalizers (`Summary`, `Notify`, `ResetTerm`) to their new category.
6. Convert or remove remaining renderers one at a time.
7. Remove `OutputManager`, filter chains, and old `Driver` only after parity
   tests cover live and replay behavior.

This staging avoids replacing lifecycle derivation, formatter behavior, process
management, and renderer semantics in one step.

## Renderer Mapping Recommendation

Current renderer disposition:

* `Default` - Split into a default renderer selector plus `Terminal`/`Text`
  rendering behavior. Reuse existing composer/theme logic where possible.
* `Summary` - Move to `Finalizer`.
* `Notify` - Move to `Finalizer`.
* `ResetTerm` - Move to `Finalizer`.
* `JUnit` - Migrate separately. Do not force it through an XML formatter unless
  the artifact boundaries naturally match JUnit XML structure.
* `DB` - Remove.
* `Driver` - Replace with watcher/lifecycle component, then remove.
* Legacy `Formatter` - Remove.
* `Logger` - Remove if the log layer already provides the durable event output.
* `TAPHarness` - Remove.
* `Server` - Stub for now. Design future server handlers to pull cached
  formatter output.

Note: keep the root `render_formatter_refactor` file authoritative. If another
discussion document says `Logger` or `Summary` continue as renderers, reconcile
that before planning.

## QVF And Verbosity

Quiet-verbose-on-failure should become renderer pull policy:

* On job start: optionally show a start line, depending on mode.
* On job sealed: fetch report.
* If pass: print/pass summary only.
* If fail: fetch events/stdout/stderr as needed, format them, then print the
  failed job line or summary.

Verbose live terminal mode can opt into tailing `events.jsonl` before seal.
Most other modes should wait for sealed artifacts.

Verbosity should decide which artifacts are requested and what detail level is
passed to formatters. It should not be implemented as a global event filter
chain.

## Process Model Notes

Each renderer process should receive enough serialized configuration to
reconstruct itself after exec. The plan should explicitly specify:

* How renderer construction args are serialized.
* How log source references are passed.
* How startup errors are reported to the parent.
* How shutdown is requested.
* How the parent distinguishes successful renderer completion from renderer
  failure.
* Whether finalizers run in process or as services.

The proposal mentions `IPC::Manager::Role::Service`; confirm that this is the
desired shutdown and supervision mechanism before coding around it.

## Tests The Plan Should Require

Minimum parity tests should cover:

* Live log terminal rendering.
* Sealed/extracted log replay rendering.
* QVF: passing job suppresses verbose event output, failing job prints it.
* Cache hit/miss behavior for sealed artifacts.
* No cache writes for tarball logs.
* Concurrent cache requests for the same artifact/formatter.
* Finalizer execution at end-of-run.
* Renderer failure propagation to the parent.

Golden-output tests will be useful for `text` output. For `tty`, test both
ANSI presence and important semantic lines rather than making every escape
sequence brittle unless the theme contract requires exact output.

## Open Questions To Resolve Before A Detailed Plan

* What is the exact artifact kind registry?
* What is the producer descriptor schema?
* Which artifact states exist: missing, partial, sealed, failed/corrupt?
* Is formatter output always bytes, or can it be structured data?
* Are `tty` and `text` separate formatters or one formatter with an ANSI option?
* Does terminal width belong in formatting or rendering?
* What settings are part of the formatter cache key?
* Are finalizers allowed to run in the parent process?
* What is the precise IPC shutdown protocol?
* What compatibility behavior must be preserved from current synthetic
  lifecycle facets?

## Suggested First Planning Deliverable

Before writing code, produce a small design plan with these sections:

1. Producer/artifact data model.
2. Watcher/lifecycle component API.
3. Formatter API and cache key/storage model.
4. Renderer process/service lifecycle.
5. Renderer-by-renderer migration table.
6. Incremental implementation stages with tests for each stage.

The plan should avoid starting with formatter modules alone. The watcher and
producer descriptor shape are the foundation for the rest of the refactor.
