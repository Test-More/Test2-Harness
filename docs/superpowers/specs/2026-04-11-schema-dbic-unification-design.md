# Schema DBIC Unification — Design

**Date:** 2026-04-11
**Status:** Approved for implementation planning
**Scope:** Refactor the DBIx::Class schema layer of Test2-Harness into a single unified set of Result modules under a new `App::Yath::Schema::DBIC` namespace.

## Motivation

The current schema layer carries five nearly-identical copies of every DBIC Result class (one per supported database: SQLite, PostgreSQL, MySQL, MariaDB, Percona), plus a dispatcher layer under `Result/` and a parallel "overlay" tree that holds custom methods. For 29 tables that's ~175 autogenerated files, 29 dispatchers, 29 overlays — ~233 files that mostly duplicate each other. Differences between backends are small enough to express inline with the existing `is_mysql()` / `is_postgresql()` / `is_sqlite()` / `is_mariadb()` / `is_percona()` helpers.

This refactor collapses those trees into **one file per Result class**, moves the entire DBIC layer under a new `::DBIC` namespace so a non-DBIC alternative schema layer can coexist in the future, and restructures per-database integration tests around `DBIx::QuickDB` so they can be written once and exercised against every backend.

## Non-goals

- Changing any SQL schema file under `share/schema/`.
- Touching `lib/App/Yath/Schema/Table/` (empty, leave alone).
- Changing business logic in `RunProcessor.pm`, `Queries.pm`, `Importer.pm`, `Sync.pm`, `Sweeper.pm`, etc. — they get namespace updates only.
- Adding or removing support for any database engine.
- Refactoring the overlay methods themselves — they transplant verbatim.

## 2. Anatomy of a unified Result module

Each of the 29 Result classes becomes a single file at `lib/App/Yath/Schema/DBIC/Result/<Name>.pm` with this structure:

```perl
use utf8;
package App::Yath::Schema::DBIC::Result::User;
our $VERSION = '2.000011';

use strict;
use warnings;
use parent 'App::Yath::Schema::DBIC::ResultBase';

use App::Yath::Schema::DBIC qw/is_sqlite is_postgresql is_mysql is_mariadb is_percona/;

# >>> BEGIN GENERATED - DO NOT EDIT <<<
# Regenerated by author_tools/regen_schema.pl from share/schema/*.sql
__PACKAGE__->load_components(
    "InflateColumn::DateTime",
    "InflateColumn::Serializer",
    "InflateColumn::Serializer::JSON",
);
__PACKAGE__->table("users");
__PACKAGE__->add_columns(
    "user_id",
    {
        data_type         => is_postgresql() ? "bigint" : "integer",
        is_auto_increment => 1,
        is_nullable       => 0,
        (is_postgresql() ? (sequence => "users_user_id_seq") : ()),
    },
    "username",
    {
        data_type   => is_postgresql() ? "citext" : "varchar",
        size        => 64,
        is_nullable => 0,
    },
    # ... more columns ...
);
__PACKAGE__->set_primary_key("user_id");
__PACKAGE__->add_unique_constraint("username_unique", ["username"]);
__PACKAGE__->has_many(
    "api_keys",
    "App::Yath::Schema::DBIC::Result::ApiKey",
    { "foreign.user_id" => "self.user_id" },
    { cascade_copy => 0, cascade_delete => 1 },
);
# ... more relationships ...
# >>> END GENERATED <<<

# Custom methods live below; regen_schema.pl never touches this region.

use Test2::Util::UUID qw/gen_uuid/;
use Carp qw/croak/;
use Crypt::Eksblowfish::Bcrypt qw(bcrypt_hash en_base64 de_base64);
use constant COST => 8;

sub new {
    my $class = shift;
    # ... transplanted from Overlay/User.pm ...
}

sub verify_password { ... }
sub set_password    { ... }
sub gen_salt        { ... }
sub gen_api_key     { ... }

1;

__END__

=pod
... POD ...
=cut
```

### Key structural points

1. **Three regions per file.**
   - **Header** (above `# >>> BEGIN GENERATED <<<`): fixed boilerplate — `use utf8`, `package`, `our $VERSION`, `use strict` / `use warnings`, `use parent`, and the `is_*` imports. Generator owns and overwrites this region on regen.
   - **Generated body** (between the markers): column definitions, primary key, unique constraints, relationships. Generator owns and overwrites this region on regen.
   - **Custom tail** (below `# >>> END GENERATED <<<`): custom `use` statements, subs, constants, POD, and the trailing `1;`. Generator never touches this region.

2. **Markers are fixed strings.** Exactly `# >>> BEGIN GENERATED - DO NOT EDIT <<<` and `# >>> END GENERATED <<<`. The generator splits each existing file on these strings; if either marker is missing, it dies loudly with the path of the offending file — never guesses.

3. **`is_*` helpers become exportable.** They currently live as class methods on `App::Yath::Schema`. They move into `App::Yath::Schema::DBIC` as exportable subs (`use Exporter 'import'` plus `@EXPORT_OK`) so Result classes can call them as bare functions inside column definitions at class-load time. They also remain callable as class methods (`App::Yath::Schema::DBIC->is_postgresql`) for existing method-call sites.

4. **Inline branching only where needed.** When all 5 backends agree on a column field (which will be most text/boolean/nullable fields), the generator emits an unconditional literal. A ternary chain over `is_postgresql()` / `is_mysql()` / `is_sqlite()` / `is_mariadb()` / `is_percona()` appears only on the keys that actually differ across backends. MariaDB/MySQL/Percona usually collapse together.

5. **Overlay content migrates into the custom tail.** Every existing `lib/App/Yath/Schema/Overlay/<Name>.pm` has its `use` statements, constants, and subs transplanted verbatim into the custom tail of the corresponding new `lib/App/Yath/Schema/DBIC/Result/<Name>.pm`. The `package App::Yath::Schema::Result::<Name>;` pragma from the old overlay files is dropped — the custom code now lives in the same file as its package declaration.

## 3. `regen_schema.pl` changes

The regen script's current responsibilities: (1) connect to each of the 5 databases, (2) run `DBIx::Class::Schema::Loader` to dump per-DB Result classes into `SQLite/`, `PostgreSQL/`, etc., (3) emit `Result/<Name>.pm` dispatcher stubs, (4) emit `Overlay/<Name>.pm` stubs if missing, (5) emit top-level connection entry-point modules.

### New flow

**Phase A — Dump each backend to a scratch directory.** Run `DBIx::Class::Schema::Loader` against all 5 databases as today, but into a temporary directory (e.g. `$tmp/SQLite/Foo.pm`, `$tmp/PostgreSQL/Foo.pm`, etc.). These intermediate dumps are throwaway and never checked in.

**Phase B — Parse each dump into a structured representation.** For each Result class, parse each per-DB dump into a canonical in-memory form: table name, ordered list of `name => hashref` columns, primary key, unique constraints, relationships. Parsing is shallow — we are reading output the generator itself produced one phase ago, so the format is stable (`__PACKAGE__->add_columns(...)`, `->set_primary_key(...)`, `->has_many(...)`, `->belongs_to(...)`, `->might_have(...)`). A hand-rolled line parser is sufficient; no `PPI` dependency.

**Phase C — Merge across backends into a unified spec.** For each Result class, walk the 5 parsed structures side by side:
- For each column field (e.g. `data_type`, `size`, `is_nullable`, `extra`), compare the value across all 5 backends. If all agree, emit the field unconditionally. If they disagree, emit a ternary chain over the `is_*` helpers covering the distinct cases. If the disagreement cannot be expressed cleanly (e.g. four different `data_type` values), emit it explicitly as a nested ternary — do not silently pick one.
- Rewrite relationship target class names from `App::Yath::Schema::Result::Foo` to `App::Yath::Schema::DBIC::Result::Foo`.
- Rewrite the `parent` / base class from `App::Yath::Schema::ResultBase` to `App::Yath::Schema::DBIC::ResultBase`.
- If the merge encounters a column or relationship in some backends but not others, die loudly with the table name, column name, and the conflict — the generator never fabricates missing metadata.

**Phase D — Emit the unified Result file.** For each table:
- **Fresh write:** if `lib/App/Yath/Schema/DBIC/Result/<Name>.pm` does not exist, write a complete file: header + `BEGIN GENERATED` marker + merged body + `END GENERATED` marker + empty custom tail (just `1;` and POD).
- **Splice update:** if the file exists, read it, locate the two markers, replace everything between them with the new merged body, and write it back. Every byte outside the marker region is preserved exactly.
- **Missing markers:** if either marker is absent from an existing file, die with the path. The generator refuses to guess where the custom tail begins.

**Phase E — Emit the connection entry points and root schema class.** Regenerate `lib/App/Yath/Schema/DBIC.pm`, `DBIC/ResultBase.pm`, `DBIC/ResultSet.pm`, and the 5 `DBIC/<Driver>.pm` connection modules. These are fully generated — no custom-code region, no markers.

**Phase F — Cleanup.** Delete the scratch dump directory. Print a summary: N Result classes written, M preserved custom tails, any skipped files.

### Removed from regen_schema.pl

- Logic that generates per-DB Result class directories in `lib/`.
- Logic that generates `Result/<Name>.pm` dispatcher stubs.
- Logic that generates `Overlay/<Name>.pm` stubs.
- Logic that generates per-DB unit test files under `t/unit/App/Yath/Schema/<Driver>/`.

### Added to regen_schema.pl

- Phases B–D (parse, merge, marker-splice).
- A `--migrate` one-shot flag that seeds each new `DBIC/Result/<Name>.pm` custom tail from the corresponding `Overlay/<Name>.pm` before running the first regen. Seeding runs only when the target file does not yet exist or its custom tail (the region below `END GENERATED`) is empty — a re-run after the initial migration leaves populated tails untouched. After the migration runs successfully and the old tree is deleted, this flag is never used again.

## 4. Consumer updates

Every file outside `lib/App/Yath/Schema/DBIC/` that references the old names is rewritten. Four categories of substitution:

1. **Result class references** (in `use`, `require`, string literals used in DBIC relationship declarations, `isa` checks, resultset source class lookups):
   - `App::Yath::Schema::Result::` → `App::Yath::Schema::DBIC::Result::`

2. **Root schema class and base classes:**
   - `App::Yath::Schema::ResultBase` → `App::Yath::Schema::DBIC::ResultBase`
   - `App::Yath::Schema::ResultSet` → `App::Yath::Schema::DBIC::ResultSet`
   - Bare `App::Yath::Schema` used as a class (`use App::Yath::Schema;`, `use base 'App::Yath::Schema';`) → `App::Yath::Schema::DBIC`. This does **not** match `App::Yath::Schema::Util`, `::Sync`, `::Sweeper`, etc.; those retain their names.

3. **Connection entry points:**
   - `App::Yath::Schema::SQLite` → `App::Yath::Schema::DBIC::SQLite`
   - Same for `PostgreSQL`, `MySQL`, `MariaDB`, `Percona`.

4. **Global loaded marker:**
   - `$App::Yath::Schema::LOADED` → `$App::Yath::Schema::DBIC::LOADED`

### Files touched (inventory from grep of `App::Yath::Schema`)

- **Schema-adjacent modules that stay named as-is but get internal updates:** `lib/App/Yath/Schema/Util.pm`, `Sync.pm`, `Sweeper.pm`, `RunProcessor.pm`, `Importer.pm`, `ImportModes.pm`, `Queries.pm`, `Config.pm`, `DateTimeFormat.pm`.
- **Server / renderer / plugin layer:** `lib/App/Yath/Server.pm`, `Server/Request.pm`, `Server/Controller/*.pm` (all 9), `Renderer/Server.pm`, `Renderer/DB.pm`, `Plugin/DB.pm`, `Options/DB.pm`.
- **Commands:** `lib/App/Yath/Command/db.pm`, `db/sync.pm`, `db/sweeper.pm`, `db/publish.pm`, `db/importer.pm`, `recent.pm`, `server.pm`.
- **Tests:** all ~60 files under `t/unit/App/Yath/Schema/`, the integration tests (`t/integration/coverage-*.t`), `t/UI/*.t`, `t/database/test.pl`, `t/0-load_all.t`.
- **Tooling:** `author_tools/regen_schema.pl` itself.

### Approach

Mechanical find-and-replace is viable for the unambiguous prefixes — `App::Yath::Schema::Result::` and `App::Yath::Schema::(SQLite|PostgreSQL|MySQL|MariaDB|Percona)` have no false-positive matches. The tricky prefixes are bare `App::Yath::Schema` and `$App::Yath::Schema::LOADED`, because those strings also appear inside names that are **not** being renamed (`App::Yath::Schema::Util`, etc.). Substitutions for those cases use anchored regexes and the changes are reviewed in chunks, not as a blanket global replace.

### Verification

After consumer updates: `perl -Ilib -c` every `.pm` and `.t` file, run `t/0-load_all.t`, then run the full per-backend test suite. The existing per-backend integration tests (once refactored per Section 5) are the ground truth for correctness.

## 5. Testing infrastructure

### Reusable test modules (new)

Namespaced under `DBIC/` so an alternative schema layer can coexist later without collisions:

```
t/lib/App/Yath/Test/DBIC/
    Database.pm   # ephemeral-DB helpers built on DBIx::QuickDB
    Schema.pm     # reusable schema smoke tests for the DBIC layer
    Coverage.pm   # reusable body of the current coverage-*.t files, DBIC-backed
```

Package names: `App::Yath::Test::DBIC::Database`, `App::Yath::Test::DBIC::Schema`, `App::Yath::Test::DBIC::Coverage`.

### Per-backend `.t` files

Naming is `dbic-<feature>-<driver>.t` — layer first, so all DBIC tests sort together and any future `mojo-`, `rose-`, or bespoke alternative can live beside them without collision.

```
t/integration/dbic-schema-sqlite.t
t/integration/dbic-schema-postgresql.t
t/integration/dbic-schema-mysql.t
t/integration/dbic-schema-mariadb.t
t/integration/dbic-schema-percona.t

t/integration/dbic-coverage-sqlite.t
t/integration/dbic-coverage-postgresql.t
t/integration/dbic-coverage-mysql.t
t/integration/dbic-coverage-mariadb.t
t/integration/dbic-coverage-percona.t
```

Each shim is a thin skip-then-delegate:

```perl
use Test2::V0;
use Test2::Tools::QuickDB;

use lib 't/lib';
use App::Yath::Test::DBIC::Coverage qw/run_coverage_tests/;

skipall_unless_can_db(driver => 'PostgreSQL');
run_coverage_tests(driver => 'PostgreSQL');

done_testing;
```

`skipall_unless_can_db` is already provided by `Test2::Tools::QuickDB` and is the correct mechanism for skipping when a backend is unavailable — the existing coverage tests use it (`t/integration/coverage-sqlite.t:25`).

### Shared module skeletons

`App::Yath::Test::DBIC::Coverage::run_coverage_tests(driver => $driver)` — contains the entire body currently duplicated between the five `coverage-*.t` files. Parameterized on driver only; everything else is identical across backends.

`App::Yath::Test::DBIC::Schema::run_schema_tests(driver => $driver)` — new module that replaces the deleted per-DB unit tests. Spins up an ephemeral database on the given driver (reusing the existing `App::Yath::Server->start_ephemeral_db` path, which already handles driver selection and schema initialization from `share/schema/`), loads the matching connection module, and exercises:
1. Every Result class loads and reports the expected columns, primary keys, and relationships from its `->result_source`.
2. Basic CRUD (`create`, `find`, `update`, `delete`) against every Result class with fixture data.
3. Every `has_many` / `belongs_to` / `might_have` relationship, with cascade rules exercised where defined.
4. The overlay-derived custom methods — `User->new` password hashing, `User->verify_password`, `User->gen_api_key`, etc. — as a regression check that the overlay migration preserved behavior.

### Deleted tests (replaced by the above)

- `t/unit/App/Yath/Schema/SQLite/*.t` (29 files) — compile-time smoke tests for per-db Result classes that no longer exist. Replaced by the stronger `dbic-schema-sqlite.t` which actually connects and exercises each class.
- `t/unit/App/Yath/Schema/MariaDB/*.t` (29 files) — same, for MariaDB.
- `t/UI/PostgreSQL.t`, `t/UI/MySQL.t` — `use_ok` smoke tests for the old per-DB connection modules. Subsumed by `dbic-schema-postgresql.t` and `dbic-schema-mysql.t`.
- Old `coverage-sqlite.t`, `coverage-pg.t`, `coverage-mysql.t`, `coverage-mariadb.t`, `coverage-percona.t` under `t/integration/` — deleted after the refactored `dbic-coverage-<driver>.t` equivalents pass. Note that `coverage-pg.t` in particular is renamed to `dbic-coverage-postgresql.t` for naming consistency.

### Tests that stay

- `t/unit/App/Yath/Schema/Result/*.t` — backend-agnostic Result behavior tests. Get their namespace references updated in the consumer-rewrite pass. If any turn out to assume a specific backend, they move into `App::Yath::Test::DBIC::Schema` and get deleted.
- `t/database/test.pl`, `t/unit/App/Yath/Schema.t`, other ancillary schema tests — namespace references updated, structure preserved.

### Regen tool scope over t/

`regen_schema.pl` currently generates per-DB unit test stubs under `t/unit/App/Yath/Schema/<Driver>/`. Under the new layout it stops generating any test files at all. The hand-written shim `.t` files and the shared modules under `t/lib/App/Yath/Test/DBIC/` are the maintained test surface.

## 6. Execution order

1. **Prep.** Create `lib/App/Yath/Schema/DBIC/`. Draft the new `App::Yath::Schema::DBIC.pm` with the exportable `is_*` helpers (moved from `App::Yath::Schema.pm`) and the existing `format_uuid_for_db` / `format_uuid_for_app` helpers.
2. **Rewrite `regen_schema.pl`** to produce the unified layout (Phases A–F from Section 3), including the one-shot `--migrate` path that seeds custom tails from the old `Overlay/` tree.
3. **Run `regen_schema.pl --migrate`** against all 5 databases. This creates the new `DBIC/Result/*.pm` files with custom tails pre-populated from the current overlays.
4. **Hand-verify a sample.** Diff 2–3 newly generated unified Result classes against the old per-DB + overlay trio — especially `User.pm`, `ApiKey.pm`, `Run.pm`, which carry the most custom code — to confirm nothing was lost.
5. **Delete the old trees.** Remove `lib/App/Yath/Schema/{SQLite,PostgreSQL,MySQL,MariaDB,Percona,Result,Overlay}/` plus `Schema.pm`, `ResultBase.pm`, `ResultSet.pm`, `SQLite.pm`, `PostgreSQL.pm`, `MySQL.pm`, `MariaDB.pm`, `Percona.pm`.
6. **Update consumers.** Rewrite every non-schema file that references the old names (Section 4). Start with `lib/`, then `t/`.
7. **Syntax check pass.** `perl -Ilib -c` every `.pm` and `.t` file; fix any misses.
8. **Load test.** Run `t/0-load_all.t` against each of the 5 backends.
9. **Author the new test modules and shims.** Write `App::Yath::Test::DBIC::{Database,Schema,Coverage}` under `t/lib/`. Refactor the 10 `dbic-*.t` shim files (5 schema + 5 coverage). Delete the replaced tests.
10. **Integration test pass.** Run the full test suite against each backend — SQLite first (no external service), then PostgreSQL, MySQL, MariaDB, Percona.
11. **Idempotency check.** Run `regen_schema.pl` (without `--migrate`) a second time and confirm a no-op diff — proves the generator is stable and the marker mechanism works correctly.

## 7. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Overlay code silently lost during migration | Step 4 hand-verification; the migration is a one-shot so this is the only chance to catch it. Commit the pre-migration overlay tree in a separate commit before running `--migrate` so `git diff` against that commit reveals any drop. |
| Column-merge logic emits subtly wrong types for edge cases | Generator dies loudly on any column where merge disagreement cannot be cleanly expressed; forces a human decision rather than silent fabrication. |
| Relationships that reference `App::Yath::Schema::Result::Foo` as a string inside a DBIC call get missed by the consumer rewrite | Step 7's `perl -c` catches missing classes; step 8 catches unloadable schemas. |
| Percona-specific UUID handling (`format_uuid_for_db` / `_for_app` on the root schema class) breaks when moved to `DBIC.pm` | Move verbatim alongside `is_*` helpers; they are small and self-contained. Exercised by `dbic-schema-percona.t`. |
| `$App::Yath::Schema::LOADED` check in a module that stays at its old name still works after rename | Those modules get updated in Section 4's consumer pass to reference the new global. |
| Per-DB unit tests silently replaced with weaker coverage | The new `dbic-schema-<driver>.t` actively exercises each Result class against a real connection — stronger than the old `use_ok` stubs, not weaker. |
| Git blame churn on the Result classes | Unavoidable for a structural refactor of this scope. Commit the file moves with `git mv` where possible, and split content rewrites from namespace rewrites into separate commits so blame can follow through the cleaner commits. |
| `regen_schema.pl --migrate` re-run after initial migration silently overwrites custom code | The `--migrate` path writes custom tails only when the target file does not yet exist or the tail is empty. A subsequent run without the flag uses the marker-splice path and leaves tails alone. |

## 8. Out of scope

- SQL schema changes of any kind.
- `lib/App/Yath/Schema/Table/` (untouched).
- Business logic in `RunProcessor`, `Queries`, `Importer`, `Sync`, `Sweeper`, `Server`, etc. (namespace updates only).
- Adding or removing DB support.
- Restructuring overlay method contents.
- Introducing an alternative (non-DBIC) schema layer — the `::DBIC` naming only reserves the room for one.

## 9. Open implementation questions

These are surfaceable decisions that can wait until the plan-writing phase:

- Whether to collapse `regen_schema.pl`'s merge + parse code into an inline single file or split into `App/Yath/Schema/DBIC/Loader/*.pm` helper modules. Inline is simpler; splitting is cleaner if the parser grows.
- Exact wording/format of the ternary chains the merger emits when three-way or four-way splits occur. Cosmetic; the generator can pick a house style and stick with it.
- Whether `App::Yath::Test::DBIC::Database` wraps or directly re-exports the relevant `DBIx::QuickDB` + `Test2::Tools::QuickDB` surface. Implementation detail.
